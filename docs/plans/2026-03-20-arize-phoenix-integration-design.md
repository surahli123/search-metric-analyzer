## Problem Statement

The Search Metric Analyzer orchestrates a multi-stage LLM pipeline (QUESTION_PARSE → UNDERSTAND → HYPOTHESIZE → DISPATCH → SYNTHESIZE) to diagnose enterprise search metric movements. The existing `trace/` module captures *what the system decided* (IC9 Invisible Decisions, seam validations) but not *what happened inside each LLM call* — prompts, responses, token counts, latency, cost. When an investigation produces a weak diagnosis, there's no way to replay the LLM interactions to understand why. Debugging is limited to reading raw JSON dicts and eval stress test scores.

## What Makes This Cool

A unified trace tree where you click into an investigation and see: the pipeline stages as parent spans → the LLM calls nested inside each stage → the domain decisions and seam validations as attributes on those spans → token costs and latency at every level. Two trace systems (enforcement + observability) working together so you can answer both "did the agent follow the rules?" and "what did the LLM actually do?"

The demo potential: show your eng lead a single Phoenix trace that tells the full story of a metric investigation — from question parsing through synthesis — with every LLM interaction, decision, and business rule validation visible. That's "whoa"-worthy.

The learning loop potential: once you can see where investigations fail (via trace replay), you can systematically build corrections — closing the gap between `corrections.yaml` and automated self-improvement.

## Constraints

- **Dev-time tool only.** Phoenix server runs as a sidecar process (`phoenix serve`), not embedded in the application. The heavy ML stack (pandas, scikit-learn, etc.) stays in the server process, not in your CLI tool.
- **Instrumentation client is lightweight.** `arize-phoenix-otel` + `openinference-instrumentation-anthropic` add OpenTelemetry SDK + protobuf. Heavier than "stdlib + PyYAML only" but acceptable for dev/debug tooling.
- **ELv2 license.** Elastic License 2.0 — fine for internal tooling, prohibits offering Phoenix as a managed service. Non-issue for this project.
- **Existing trace system is untouched for enforcement.** InvestigationTrace, SeamSpan, and the 17 business rules in contracts/ continue to serve their enforcement purpose. Phoenix is additive observability, not a replacement.
- **Layer 3 boundary.** Per architecture rules, trace/ depends only on itself. The Phoenix integration layer sits in harness/ (Layer 4), not in trace/ (Layer 3).

## Premises

1. The primary need is LLM call visibility (prompts, responses, tokens, latency) — not replacing the existing trace/contracts enforcement system.
2. Phoenix should COMPLEMENT your existing trace system, not replace it. SeamSpan + 17 business rules + IC9 tracing serve enforcement; Phoenix serves observability. They're orthogonal.
3. The "stdlib + PyYAML only" constraint bends for dev-time instrumentation dependencies (arize-phoenix-otel, openinference-instrumentation-anthropic, opentelemetry-sdk).
4. Phoenix should be a DEV-TIME tool — sidecar pattern keeps the heavy server out of the application process.

## Approaches Considered

### Approach A: Phoenix Sidecar — Auto-Instrument Only
- Install lightweight Phoenix instrumentation client, auto-patch the Anthropic SDK, run Phoenix server as sidecar
- Effort: S (human: ~2 hours / CC: ~15 min) | Risk: Low
- Pros: Fastest path to LLM visibility, zero changes to core/contracts/trace
- Cons: Flat traces (no stage grouping), domain decisions invisible in Phoenix, two disconnected trace systems
- Completeness: 5/10

### Approach B: Phoenix + Custom Stage Spans (Chosen)
- Everything in A, plus custom OpenInference CHAIN spans per pipeline stage, LLM calls nested inside them, domain decisions as span attributes, seam validations as GUARDRAIL spans
- Effort: M (human: ~1 week / CC: ~30 min) | Risk: Medium
- Pros: Unified trace tree, full story in one view, demo-ready, auditable IC9 decisions
- Cons: Dual-emit overhead, impedance mismatch between TypedDicts and OTel attributes, more dependency surface
- Completeness: 9/10

### Approach C: DIY Trace Viewer — No Phoenix
- Add LLM call capture to InvestigationTrace, build trace viewer into existing web app Trace tab
- Effort: L (human: ~2 weeks / CC: ~2 hours) | Risk: Medium
- Pros: Zero dependencies, full domain control, extends existing Trace tab
- Cons: Reinvents what Phoenix provides for free, basic UI compared to Phoenix
- Completeness: 7/10

## Recommended Approach

**Approach B: Phoenix + Custom Stage Spans.** It's the only approach that gives a unified view — LLM calls AND domain decisions in the same trace tree. The extra work over A is modest (CC: ~30 min vs ~15 min), and it delivers the debugging power and demo-readiness needed for both personal workflow and eng lead presentations.

### Span Mapping

| Your Concept | OpenInference Span Kind | Attributes |
|---|---|---|
| Pipeline stage (UNDERSTAND, etc.) | CHAIN | `stage`, `mode` (Simple/Medium/Complex) |
| LLM call (Anthropic SDK) | LLM (auto-instrumented) | `llm.model_name`, `llm.token_count.*`, messages |
| Core tool execution (decompose, anomaly) | TOOL | `tool.name`, `decision`, `value` |
| Seam validation | GUARDRAIL | `tier` (hard/soft/retry), `passed`, `violations` |
| IC9 Invisible Decision | Span attribute on parent | `ic9.decision`, `ic9.value`, `ic9.code_enforced` |
| DAG parallel dispatch | AGENT | `executor`, `agents_dispatched`, `circuit_breaker` |

### Key Integration Points

1. **`harness/orchestrator.py` — `run()` and `run_v2()`**: Wrap each stage call in an OTel CHAIN span. The Anthropic auto-instrumentor captures LLM calls nested inside.
2. **`harness/llm.py`**: The Anthropic client is auto-instrumented by `AnthropicInstrumentor().instrument()` — no code changes needed here.
3. **`trace/helpers.py`**: Add a sibling `emit_otel_span()` helper that dual-emits to both InvestigationTrace and OTel. Core tools call this instead of `emit_deterministic_span()`.
4. **`contracts/seam_validator.py`**: After validation, emit a GUARDRAIL span with pass/fail + tier + violations.
5. **`harness/dag_executor.py`**: Wrap parallel dispatch in an AGENT span with child CHAIN spans per dispatched agent.

### Dependency Budget

**Instrumentation (in your process):**
- `arize-phoenix-otel` — thin OTel wrapper (~5 transitive deps)
- `openinference-instrumentation-anthropic` — Anthropic SDK patcher
- `opentelemetry-sdk`, `opentelemetry-exporter-otlp` — standard OTel

**Server (separate process, NOT in your deps):**
- `arize-phoenix` — full server with pandas, scikit-learn, FastAPI, etc.
- Installed separately: `pip install arize-phoenix` in its own venv or Docker

### Graceful Degradation

Phoenix integration must be optional. If `arize-phoenix-otel` is not installed or Phoenix server is not running:
- No crash, no import error — guard all imports with try/except
- `emit_otel_span()` becomes a no-op (same pattern as `emit_deterministic_span()` when trace is None)
- InvestigationTrace continues to work exactly as it does today

## Open Questions

1. **Should Phoenix traces be correlated with InvestigationTrace IDs?** You could set `trace_id` in OTel to match `InvestigationTrace.trace_id`, making it possible to look up the same investigation in both systems. Recommended: yes.
2. **Should the web app Trace tab link to Phoenix?** If Phoenix is running, the Trace tab could include a "View in Phoenix" link for the current investigation. Nice-to-have for v2.
3. **Eval integration:** Should `eval/run_stress_test.py` also emit to Phoenix so you can visually compare all 7 scenario traces? High value but adds Phoenix as an eval dependency.
4. **Token cost calculation:** Phoenix auto-tracks token counts but not dollar costs (model pricing changes). Should you add cost estimation or leave that to Phoenix's built-in cost tracking?

## Success Criteria

1. **Running `python -m harness.orchestrator` with Phoenix server up produces a visual trace tree** showing: investigation root → pipeline stages → LLM calls + domain decisions → seam validations
2. **Token counts visible per stage** — can answer "SYNTHESIZE used 3x more tokens than UNDERSTAND"
3. **Graceful degradation** — removing Phoenix dependencies causes zero breakage in existing tests (all 1,348 pass)
4. **Demo-ready** — can show an eng lead the Phoenix UI and they understand the investigation flow without explanation
